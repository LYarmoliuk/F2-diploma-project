# 2. Актуальність та проблематика

У професійній діяльності фахівців ІТ значну роль відіграють комунікаційні навички, зокрема надання конструктивного зворотного зв’язку, ведення переговорів із клієнтами, вирішення конфліктних ситуацій, аргументоване відстоювання позиції та комунікація в умовах обмежених ресурсів або термінів. Недостатньо сформовані навички такої взаємодії можуть ускладнювати командну комунікацію та взаємодію з клієнтами.

Основною проблемою є **відсутність доступного програмного середовища для систематичного та безпечного практичного тренування складних комунікаційних ситуацій**. Теоретичні матеріали дозволяють ознайомитися з моделями комунікації, але не забезпечують повноцінної практики прийняття рішень у динамічному діалозі. Реальні рольові тренування потребують участі іншої людини або тренера та не завжди забезпечують можливість багаторазового проходження однакової ситуації з використанням різних стратегій поведінки.

З погляду інженерії програмного забезпечення проблема полягає у необхідності розробки **stateful інтерактивної системи**, у якій кожна відповідь користувача впливає на подальший стан діалогу та поведінку віртуального співрозмовника. Система повинна підтримувати контекст діалогу, моделювати стан персонажа, аналізувати текстові відповіді користувача, формувати структуровані запити до зовнішнього LLM-сервісу та обробляти його недетерміновані результати.

Додатковою інженерною проблемою є забезпечення надійності взаємодії із зовнішнім AI-сервісом. Отримані від LLM дані не можуть передаватися безпосередньо до бізнес-логіки системи, оскільки зовнішній сервіс може бути тимчасово недоступним, повертати некоректні або неповні дані чи перевищувати встановлені обмеження. Тому програмна система повинна забезпечувати валідацію структурованих AI-відповідей, обробку помилок, контроль часу очікування та обмежені повторні запити.

Таким чином, **Panel Talk** спрямований на створення програмного середовища для багаторазового тренування складних комунікаційних сценаріїв із використанням AI-керованих персонажів, керуванням станом діалогу, автоматизованим аналізом відповідей та формуванням зворотного зв’язку.

# 3. Сформована ідея продукту

**Panel Talk** — вебплатформа для тренування комунікаційних навичок шляхом проходження інтерактивних діалогових сценаріїв з AI-керованими персонажами.

Система моделює комунікаційну ситуацію у форматі **динамічного цифрового коміксу**. Кожна репліка AI-персонажа представлена окремою візуальною панеллю із текстом, персонажем та його поточним емоційним станом.

Користувач формує власні відповіді у вигляді **вільного текстового вводу**. Backend передає контекст діалогу до AI-сервісу, який генерує наступну репліку персонажа та структуровані характеристики його стану.

Розширення взаємодії: передбачається дослідження можливості додавання голосового режиму взаємодії з AI-персонажами, включно з розпізнаванням голосу користувача та озвученням відповідей AI.

Отримана AI-відповідь проходить обробку через **AI Integration Layer**, який відповідає за:

- формування та передачу запиту;
- обробку timeout;
- контрольовані повторні запити;
- обробку помилок зовнішнього сервісу;
- parsing структурованої відповіді;
- schema-based validation;
- перетворення результату у внутрішню модель системи.

Приклад структурованої AI-відповіді:

```
{
  "reply_text":"...",
  "emotion":"defensive",
  "intensity":0.6,
  "tension_delta":0.1
}
```

Отримані параметри використовуються для оновлення **стану діалогу (Dialogue State)** та формування наступного кроку взаємодії.

Система також аналізує відповіді користувача за визначеними комунікаційними категоріями:

- `assertive`;
- `aggressive`;
- `passive`;
- `empathetic`.

Результат класифікації зберігається як частина результатів проходження сценарію та використовується для формування підсумкового аналізу.

Після завершення сценарію система формує покроковий recap, що містить аналіз відповідей користувача, вплив окремих реплік на розвиток ситуації, альтернативні формулювання та узагальнення результатів проходження.

### Архітектурна модель

Для реалізації проєкту передбачається **клієнт-серверна архітектура з модульним монолітним backend**, що дозволяє розділити відповідальність між функціональними компонентами системи без введення зайвої розподіленої інфраструктури.

```
                         ┌──────────────────────┐
                         │       Vue 3          │
                         │                      │
                         │ Comic UI             │
                         │ Session State        │
                         │ History / Recap      │
                         └──────────┬───────────┘
                                    │
                               HTTPS / REST
                                    │
                                    ▼
┌────────────────────────────────────────────────────────┐
│                  FastAPI Backend                       │
│                                                        │
│  ┌──────────────┐      ┌───────────────────────────┐  │
│  │ API Layer    │      │ Authentication / Authz    │  │
│  └──────┬───────┘      └───────────────────────────┘  │
│         │                                               │
│         ▼                                               │
│  ┌──────────────────────────────────────────────────┐  │
│  │ Service Layer                                    │  │
│  │ DialogueService / AnalysisService / RecapService │  │
│  └──────────────┬───────────────────┬───────────────┘  │
│                 │                   │                  │
│                 ▼                   ▼                  │
│       ┌─────────────────┐   ┌─────────────────────┐  │
│       │ Repository      │   │ AI Integration      │  │
│       │ Layer           │   │ Layer               │  │
│       │                 │   │                     │  │
│       │ SQLAlchemy      │   │ Prompt / Context    │  │
│       │ PostgreSQL      │   │ LLM Client          │  │
│       └────────┬────────┘   │ Timeout / Retry      │  │
│                │            │ Validation           │  │
│                │            │ Error Handling       │  │
│                │            └──────────┬──────────┘  │
└────────────────┼───────────────────────┼─────────────┘
                 │                       │
                 ▼                       ▼
          ┌──────────────┐        ┌──────────────┐
          │ PostgreSQL   │        │   LLM API    │
          └──────────────┘        └──────────────┘
```

Таке архітектурне рішення забезпечує separation of concerns між HTTP-рівнем, бізнес-логікою, persistence та взаємодією із зовнішнім AI-сервісом.

**Modular Monolith** обрано як компроміс між структурованістю системи та складністю її експлуатації. Функціональні модулі мають чітко визначені відповідальності, але залишаються частинами єдиного backend-додатка.

# 4. Core Features

### 1. Каталог комунікаційних сценаріїв

Користувач може переглядати та обирати сценарій для тренування.

Сценарій містить:

- назву;
- категорію;
- опис ситуації;
- складність;
- персонажа;
- початкові умови діалогу.

Приклади категорій:

- надання негативного feedback;
- конфлікт у команді;
- переговори з клієнтом;
- ескалація проблеми;
- відмова від нереалістичного запиту.

### 2. Інтерактивне проходження діалогу

Користувач проходить сценарій у форматі динамічного коміксу.

Кожна репліка персонажа генерується залежно від:

- попередніх реплік;
- поточного стану діалогу;
- характеристик персонажа;
- відповіді користувача.

Візуальний стан персонажа змінюється відповідно до отриманого від AI емоційного тегу.

### 3. Генерація AI-реплік у реальному часі

Backend інтегрується із зовнішнім LLM API через AI Integration Layer.

Основний потік обробки:

```
User Response
      │
      ▼
Dialogue Context
      │
      ▼
AI Integration Layer
      │
      ├── request
      ├── timeout
      ├── retry
      ├── parsing
      └── validation
      │
      ▼
Validated AI Response
      │
      ▼
Dialogue State Update
      │
      ▼
Frontend
```

Система не передає необроблену відповідь LLM безпосередньо до клієнта. Отримані дані проходять схематичну валідацію та перетворюються у внутрішню модель системи.

Для transient failures передбачається обмежена кількість повторних запитів із backoff. Помилки, які не можуть бути усунені повторним запитом, перетворюються на контрольовані помилки API.

### 4. Аналіз комунікаційного стилю користувача

Система визначає комунікаційний стиль сформованої користувачем відповіді.

Передбачені категорії:

- `assertive`;
- `aggressive`;
- `passive`;
- `empathetic`.

Результат класифікації використовується для подальшого аналізу проходження сценарію.

### 5. Візуалізація динаміки діалогу

Система відображає:

- послідовність реплік;
- емоційний стан персонажа;
- динаміку напруги;
- відповіді користувача;
- зміни стану ситуації.

Таким чином, історія діалогу залишається доступною як єдина послідовність комікс-панелей.

### 6. Автоматизований аналіз діалогів

Після завершення сценарію система формує recap із:

- покроковим аналізом відповідей;
- визначенням комунікаційного стилю;
- поясненням впливу окремих відповідей;
- аналізом розвитку конфлікту;
- прикладами альтернативних формулювань;
- узагальненням результатів проходження.

Для аналізу можуть використовуватися моделі асертивної комунікації та ненасильницької комунікації (NVC).

### 7. Збереження історії проходжень

Система зберігає результати завершених сесій користувача.

Це дозволяє:

- переглядати попередні проходження;
- повторювати сценарії;
- порівнювати результати;
- аналізувати зміни показників комунікаційних навичок.

# 5. Попередній інструментарій та технологічний стек

### Мови програмування

- **TypeScript** — frontend;
- **Python** — backend та інтеграція AI;
- **SQL** — робота з реляційними даними.

### Frontend

- **Vue 3**;

- **Python**;
- **FastAPI**;

- **SQLAlchemy** — ORM;
- **REST API**;
- **OpenAPI/Swagger** — документування API.

### AI

- Claude API — попередньо обраний постачальник LLM;
- Structured Output / JSON;
- prompt-based character modeling;
- AI-based classification of communication style;
