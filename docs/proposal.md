# 2. Актуальність та проблематика

**Контекст.** У професійній діяльності ІТ-фахівців комунікаційні навички безпосередньо впливають на якість командної роботи: надання конструктивного зворотного зв'язку, переговори з клієнтами, розв'язання конфліктів, аргументація позиції та комунікація в умовах обмежених ресурсів чи термінів. Недостатній рівень цих навичок знижує ефективність командної взаємодії та ускладнює роботу з клієнтами.

**Проблема.** Бракує доступного програмного середовища для безпечного багаторазового тренування складних комунікаційних ситуацій. У реальній взаємодії помилка може вплинути на робочі стосунки та репутацію. Наявні засоби навчання мають такі обмеження:

- теоретичні матеріали (лекції, статті) знайомлять з моделями комунікації, але не забезпечують практики прийняття рішень у діалозі та зворотного зв'язку;
- рольові тренування з тренером потребують значних ресурсів, не масштабуються на велику кількість користувачів і не дають змоги точно повторити ситуацію з іншою стратегією поведінки;
- сценарні симулятори з фіксованим деревом діалогу не реагують на стиль комунікації користувача, тому слабко відтворюють реальну взаємодію.

**Інженерна складність.** Адаптивний тренажер має динамічно моделювати комунікаційну ситуацію, зберігати контекст діалогу, генерувати реакції віртуального співрозмовника, відображати зміни його емоційного стану та аналізувати відповіді користувача. Це передбачає розв'язання таких задач:

1. Забезпечення відповідності виходу недетермінованої мовної моделі JSON-схемі з контрольованою обробкою відхилень (повторний запит, значення за замовчуванням, облік кожного випадку).
2. Керування станом діалогу та контекстним вікном із контролем затримок і вартості запитів; ідемпотентність ходів.
3. Класифікація стилів комунікації (`assertive`, `aggressive`, `passive`, `empathetic`), відображення кроків діалогу на етапи моделі ненасильницького спілкування (NVC) та вимірювання точності класифікації.
4. Асинхронна генерація аналітичного розбору після завершення сесії без блокування інтерфейсу.
5. Безпека: захист від prompt injection, обмеження виходу моделі, контроль доступу до даних, мінімізація персональних даних, обмеження витрат на виклики LLM.
6. Відмовостійка інтеграція із зовнішнім LLM API та спостережуваність системи (логи, метрики викликів).

**Мета продукту:** створити середовище для багаторазового відпрацювання складних комунікаційних сценаріїв з автоматизованим аналізом дій користувача.

# 3. Сформована ідея продукту

«Panel Talk» — вебплатформа для тренування комунікаційних навичок через діалогові сценарії з AI-керованими персонажами.

Діалог відображається як інтерактивний комікс: кожна репліка персонажа є окремою панеллю з текстом, зображенням персонажа та його поточним емоційним станом. Користувач відповідає вільним текстовим вводом, тому траєкторія діалогу не обмежена наперед заданим набором варіантів.

На кожному ході backend передає контекст діалогу до LLM-сервісу, який повертає структурований результат: текст репліки персонажа, емоцію, її інтенсивність, зміну напруги та класифікацію стилю поточної репліки користувача. Відповідь валідується за JSON-схемою; недопустимі значення замінюються на `neutral`, а кожна заміна фіксується в метриках.

**Детермінований шар доменної логіки.** Результат сценарію визначає не модель, а код системи:

- підсумкове значення напруги обчислює backend: `tension_delta` обмежується за максимальним кроком, згладжується, а результат приводиться до діапазону [0, 1];
- стан сесії описано скінченним автоматом: `CREATED → IN_PROGRESS → (RESOLVED | ESCALATED | ABANDONED) → RECAP_PENDING → (RECAP_READY | RECAP_FAILED)`. Умови завершення задаються порогами напруги (наприклад, `tension ≥ 0.9` дає `ESCALATED`, `tension ≤ 0.2` протягом двох ходів дає `RESOLVED`) та лімітом ходів;
- контекст для LLM формується за визначеною стратегією: системний промпт, профіль персонажа, стислий стан (поточна напруга, ключові факти) та останні N ходів.

Після завершення сценарію окремий воркер у фоновому режимі формує розбір: вплив відповідей користувача на співрозмовника, етапи NVC, альтернативні формулювання та підсумок.

**Архітектурна модель.** Система має модульну клієнт-серверну архітектуру з централізованим backend на базі FastAPI. Доменна логіка ізольована від LLM-провайдера адаптером, що також дозволяє підміняти його мок-реалізацією в тестах. Постсесійна аналітика виконується окремим воркером через чергу завдань, тому тривала генерація не блокує інтерфейс.

```
┌─────────────────────────────┐
│      Vue 3 Web Client       │
│  UI / Comic / Session State │
└──────────────┬──────────────┘
               │ HTTPS / REST
               ▼
┌─────────────────────────────┐
│       FastAPI Backend       │
│ ┌─────────┐ ┌─────────────┐ │
│ │ Dialog  │ │    Auth     │ │
│ │ Module  │ │   Module    │ │
│ └─────────┘ └─────────────┘ │
│ ┌─────────┐ ┌─────────────┐ │
│ │   LLM   │ │    Recap    │ │
│ │ Adapter │ │   Module    │ │
│ └─────────┘ └─────────────┘ │
└───┬─────────────┬─────────┬─┘
    │             │         │
    ▼             ▼         ▼
┌──────────┐  ┌───────┐  ┌─────────┐
│PostgreSQL│  │ Redis │  │ LLM API │
└──────────┘  └───┬───┘  └────▲────┘
                  │ черга     │
                  ▼           │
          ┌────────────────┐  │
          │ Analytics      │──┘
          │ Worker         │
          └────────────────┘
```

**Тип системи:** клієнт-серверний вебзастосунок із LLM-керованою доменною логікою, ізольованим інтеграційним шаром та асинхронним конвеєром постобробки.

**Інфраструктурний контур:** контейнеризація, CI/CD з автоматизованим тестуванням і перевіркою безпеки, розгортання в хмарі, структуроване логування та метрики (Observability).

# 4. Core Features

**1. Каталог комунікаційних сценаріїв.** Перегляд і вибір сценаріїв за категоріями (надання негативного зворотного зв'язку, конфлікт у команді, переговори з клієнтом, ескалація проблеми, відмова від нереалістичного запиту) та складністю. Сценарій містить назву, категорію, опис ситуації, профіль персонажа, початкові умови діалогу та системний промпт-характер. Сценарії та персонажі (включно з відповідністю емоцій спрайтам) зберігаються як версіоновані YAML/JSON-конфігурації, а не як таблиці БД.

**2. Динамічна генерація реплік персонажа.** Backend передає до LLM API контекст діалогу: профіль персонажа, стислий стан, останні репліки та поточну відповідь користувача. Модель повертає структурований результат через tool use:

```json
{  "reply_text": "...",  "emotion": "defensive",  "intensity": 0.6,  "tension_delta": 0.1,  "user_style": "assertive",  "style_confidence": 0.82}
```

Конвеєр обробки: виклик із таймаутом → валідація за Pydantic-схемою → не більше однієї повторної спроби з корекційним повідомленням → fallback (`neutral` для емоції) → запис інциденту. Типи відхилень (невалідний JSON, значення поза переліком, порожня репліка, перевищення довжини) лічаться окремо. Для транзієнтних помилок (429, 5xx, timeout) застосовується обмежений retry з експоненційною затримкою. Ідемпотентний ключ ходу (`turn_id`) запобігає дублюванню ходу та повторному виклику LLM при повторному запиті клієнта.

**3. Вільний ввід і класифікація комунікаційного стилю.** Користувач формулює відповіді довільним текстом. Поточна репліка користувача класифікується моделлю за категоріями `assertive`, `aggressive`, `passive`, `empathetic` у межах того самого структурованого виклику. Результат зберігається зі значенням впевненості й використовується в розборі. Якість класифікації оцінюється окремо (див. нефункціональні вимоги).

**4. Керування станом діалогу.** Скінченний автомат сесії, детермінований підрахунок напруги, умови завершення сценарію, блокування конкурентних ходів в межах однієї сесії та політика контексту (останні N ходів зі стисленим станом).

**5. Візуалізація діалогу у форматі коміксу.** Клієнт відображає діалог як вертикальну стрічку панелей, що додаються донизу з автопрокруткою: спрайт персонажа (емоція та інтенсивність), бульбашки мовлення, відповіді користувача та шкала напруги. Після завершення вся стрічка залишається доступною для перегляду.

**6. Асинхронний аналіз діалогу (recap).** Після завершення сценарію завдання ставиться в чергу й виконується воркером. Завдання має статуси `pending → running → done | failed`, обмежену кількість повторів, ідемпотентність (повторний запуск не створює дубль) і можливість перезапуску. Клієнт отримує статус через polling із зростаючим інтервалом. Recap містить: покроковий аналіз відповідей, пояснення впливу на співрозмовника, віднесення до етапів NVC (спостереження, почуття, потреба, прохання), альтернативні формулювання та підсумок із діаграмою розподілу стилів.

**7. Автентифікація, захист і історія проходжень.** JWT-автентифікація, перевірка власності ресурсу на кожному ендпоїнті сесії, rate limiting (Token Bucket на Redis), ліміти ходів на сесію та сесій на користувача на добу, обмеження довжини вводу, розмежування ролей у запиті до LLM, обмеження та перевірка виходу моделі (довжина, вихід із ролі), мінімізація персональних даних. Результати завершених сесій зберігаються в PostgreSQL; доступні перегляд історії, повторне проходження та порівняння результатів одного сценарію.

**Нефункціональні вимоги.** Цільові значення попередні й уточнюються за результатами вимірювань; досягнення цілі не є умовою, порівняння «ціль проти факту» входить до результатів роботи.

| Показник | Метод вимірювання | Цільове значення |
| --- | --- | --- |
| Частка відповідей LLM, валідних з першої спроби | Лічильники в `llm_calls` та метриках | ≥ 95 % |
| Частка fallback-підстановок | Лічильник по типах відхилень | фіксується, ціль уточнюється |
| Затримка генерації репліки (p95) | Метрики викликів, k6 (за наявності часу) | ≤ 5 с |
| Вартість токенів на сесію | Облік токенів у `llm_calls` | визначається експериментом зі стратегіями контексту |
| Точність класифікації стилів | 100–150 реплік, розмітка двома особами, Cohen's κ, accuracy, macro-F1, матриця помилок | перевищення базової лінії (правила за ключовими словами) |
| Стійкість до prompt injection | Автоматизований набір 15–30 атак | ≥ 90 % відбитих |
| Покриття тестами доменного шару | pytest-cov | ≥ 80 % |
